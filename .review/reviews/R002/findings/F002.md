# F002 — Blocked and Deferred Tasks have no defined outgoing transitions

Status: closed

Severity: medium

Location:
SPEC.md §9.10 (transition table, lines 448–459)

## Observation

The Task transition table defines entry into `Blocked` and `Deferred`
(`any (non-terminal) → Blocked | Implementer` and `any (non-terminal) → Deferred |
Implementer`) but defines no outgoing transitions for either state other than the
generic `any → Cancelled`.

§9.7 defines `Blocked` as "Work cannot proceed because of an external dependency or
unresolved blocker" and §9.8 defines `Deferred` as "The Task is intentionally
postponed" — both imply the Task eventually resumes. There is no `Blocked → In
Progress`, `Deferred → In Progress`, or `Deferred → Planned` row, so a Task that
enters either state cannot legally resume implementation. The lifecycle model is
incomplete.

## Recommendation

Add explicit outgoing transitions for `Blocked` and `Deferred`, for example
`Blocked → In Progress | Implementer | The blocker is resolved` and `Deferred →
Planned | Implementer | Work resumes`. If resumption is intentionally left to the
Implementer, state that and keep the table consistent.

## Decision

Status: accepted

Rationale:
Add `Blocked → In Progress` and `Deferred → Planned` rows to the §9.10 transition table.
